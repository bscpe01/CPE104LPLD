Lab 1 · Introduction · ILO 1

The Program Development Cycle

Every program, from a calculator app to an embedded controller, goes through the same cycle.

  1. 1Understand the problem
  2. 2Plan the logicLab 1 is here
  3. 3Code the program
  4. 4Translate to machine languagecompiler
  5. 5Test the program
  6. 6Put into production
  7. 7Maintain the program
New requirements send you back to step 1

Planning tools (step 2)

  • Algorithm: the steps in plain words
  • Pseudocode: structured, English-like code
  • Flowchart: the steps as a diagram

Syntax errors

Breaking the rules of the language (e.g., a missing ; in C++). The compiler catches them in step 4.

Logic errors

The program runs but gives wrong results. They show up in testing (step 5). Good planning prevents them.

Based on Farrell, Programming Logic and Design (10th ed.), the course's main reference.

Suggested time: about 7 min

Teaching tips

  • Use a CpE example such as a digital thermometer. Understand the problem (range? °C or °F?), plan the logic, write the firmware, compile, test it in ice water and boiling water, ship it, then maintain it with firmware updates.
  • Stress that the cycle never really ends: maintenance brings new requirements, and you start again from understanding.
  • Lab 1 covers step 2. Lab 2 (Basics of C++) moves on to steps 3 and 4.

Common student pitfalls

  • Believing that a program which compiles is correct. No syntax errors does not mean no logic errors.
  • Skipping "Understand the problem". It is the most common reason lab answers are wrong.

Ask the class

  • "Which phase costs the most time and money in real software?" (Maintenance.)
  • "Why is a logic error harder to find than a syntax error?" (Nothing warns you; the output is simply wrong.)

Lab 1 · Algorithms · ILO 2

What is an Algorithm?

An algorithm is a finite sequence of well-defined, computer-implementable instructions, typically to solve a problem.

An algorithm is a step-by-step procedure for solving a problem.

An algorithm is not the complete code or program. It is just the core logic of a problem.

FiniteStops after a limited number of steps.
Well-definedEvery step is clear and unambiguous.
InputTakes zero or more values in.
OutputProduces at least one result.
EffectiveEach step can actually be carried out.

Engineering example

Total resistance of three resistors in series

RT = R1 + R2 + R3

  1. Start.
  2. Read the values of R1, R2, and R3.
  3. Compute RT = R1 + R2 + R3.
  4. Display RT.
  5. End.

Plain numbered steps, with no C++ syntax. That is the core logic.

Suggested time: about 6 min

Teaching tips

  • Play "Human Robot". A volunteer dictates steps for cooking instant noodles and you follow them literally. Vague steps ("add water": how much, when?) show why every step must be well-defined.
  • The three definitions come straight from the Lab 1 deck. The five traits are the standard properties (after Knuth) and give students a checklist for their own algorithms.

Common student pitfalls

  • Vague steps such as "solve the problem" or "get the answer".
  • Steps in the wrong order, e.g., displaying RT before computing it.
  • Writing real C++ and calling it an algorithm.
  • No stopping point, so the algorithm is not finite.

Ask the class

  • "Is Lather, rinse, repeat on a shampoo bottle a valid algorithm?" No. It never ends, so it is not finite.

Lab 1 · Algorithms

Classification of Algorithms by Structure

Every algorithm is built from three control structures, each with one entry and one exit.

1 Sequence

Steps run one after another, in order.

INPUT a, b
SET sum = a + b
DISPLAY sum

2 Branching (Selection)

Chooses one of two paths using a TRUE/FALSE condition.

IF age >= 18 THEN
    DISPLAY "Adult"
ELSE
    DISPLAY "Minor"
ENDIF

3 Loop (Repetition)

Repeats steps while a condition stays TRUE.

SET count = 1
WHILE count <= 5 DO
    DISPLAY count
    SET count = count + 1
ENDWHILE

Suggested time: about 8 min

Teaching tips

  • Everyday examples. Sequence: your morning routine. Selection: "If it's raining, bring an umbrella; otherwise wear sunglasses." Loop: "Keep stirring until the sauce thickens."
  • Böhm and Jacopini (1966) proved that any algorithm can be built from these three structures alone, so mastering them means mastering logic.
  • Point out that each diagram has exactly one arrow in and one arrow out. That property is what makes it structured.
  • The syllabus covers these structures in C++ in Labs 5–8.

Common student pitfalls

  • Confusing selection with repetition. IF runs its block at most once; WHILE may run it many times.
  • Forgetting to update the loop variable (count = count + 1), which creates an infinite loop.
  • Leaving out ENDIF or ENDWHILE, so the end of the block is unclear.

Ask the class

  • "To compute a final grade for each of 40 students, which structures do we need?" (A loop with selection inside.)

Lab 1 · Algorithms · ILO 2

How to Write an Algorithm

  1. Understand the ProblemClarify the requirements, constraints, and expected outcome. Break the problem into smaller parts.
  2. Determine the Input and OutputWhat data comes in (format, type, range)? What result goes out?
  3. Choose an Algorithm ParadigmPick the general approach that suits the problem (see below).
  4. Develop a High-Level AlgorithmOutline the main steps, e.g., in pseudocode, without syntax details.
  5. Refine the AlgorithmCheck correctness, efficiency, and readability. Handle edge cases.
  6. Implement the AlgorithmTranslate it into a programming language (C++ in this course).
  7. Test and DebugTry typical, boundary, and exceptional inputs. Fix any errors.
  8. Analyze and OptimizeConsider time and space complexity. Remove bottlenecks.
Common paradigms: Divide & ConquerGreedyDynamic ProgrammingBacktrackingBranch & BoundRandomized

Suggested time: about 6 min

Teaching tips

  • Steps 4 and 5 together are stepwise refinement (top-down design): start with big steps, then add detail.
  • Paradigms, briefly. Divide & Conquer splits a problem, solves the parts, then combines them. Greedy takes the best local choice each step. Dynamic Programming solves overlapping subproblems once and stores the results. Backtracking tries a choice and undoes it if it fails. Branch & Bound prunes branches that can't win. Randomized uses randomness for speed. Lab 1 problems only need straightforward sequence, selection, and loops.
  • Step 6 example from the original deck notes: factorial. if n is 0 or 1 return 1, else result = 1; for i from 2 to n: result = result * i.

Common student pitfalls

  • Jumping straight to coding (step 6) without listing inputs and outputs, which leads to missing variables.
  • Testing only the "happy path" (a grade of 95) and never a boundary (exactly 90 or 89).

Ask the class

  • "What are the inputs and outputs of an ATM withdrawal?" (Inputs: card, PIN, amount. Outputs: cash, receipt, new balance, or an error.)

Lab 1 · Algorithms · Engineering problem

Applying the 8 Steps: Ohm's Law

Find the current I through a resistor, given the voltage V and resistance R, where I = V ÷ R.

StepApplied to Ohm's Law
1 · UnderstandCurrent depends on voltage and resistance: I = V / R.
2 · Input / OutputIn: voltage (V), resistance (Ω). Out: current (A).
3 · ParadigmDirect computation: a sequence with one decision.
4 · High-levelGet V and R, compute I, display I.
5 · RefineWhat if R = 0? Division by zero, so add a check.
6 · ImplementWrite the pseudocode on the right (C++ comes later).
7 · Test12 V, 4 Ω gives 3 A. 9 V, 0 Ω gives an error message.
8 · AnalyzeA fixed number of steps, clear names, and bad input handled.
 
// This program computes the current in a circuit
// using Ohm's Law (I = V / R).
START
    PROMPT "Enter voltage (V) and resistance (ohms):"
    INPUT voltage, resistance
    IF resistance = 0 THEN
        DISPLAY "Error: resistance cannot be zero."
    ELSE
        COMPUTE current = voltage / resistance
        DISPLAY "Current = ", current, " A"
    ENDIF
END

Suggested time: about 8 min

Teaching tips

  • This example serves ILO 2 (algorithms for engineering problems). Cover the right half and ask the class to supply each step first.
  • Run the tracer with 12 V and 4 Ω, then 9 V and 0 Ω. The division-by-zero guard is the payoff of step 5 (Refine).
  • Connect it to their physics and circuits classes. Engineers write algorithms for formulas they already know.

Common student pitfalls

  • Dividing in the wrong order (R / V).
  • Forgetting units in the output.
  • Never handling R = 0.
  • Reusing one variable name for two different quantities.

Ask the class

  • "What other invalid input should we guard against?" (Negative resistance.)

Lab 1 · Pseudocode · ILO 3

What is Pseudocode?

An outline of a program, written in a form that can easily be converted into real programming statements.

An informal language that has no syntax rules and is not meant to be compiled or executed.

A high-level, structured language that describes algorithms in a human-readable, language-independent way. It is a bridge between natural language and programming code.

Why use pseudocode?

Language independenceThe same plan converts to C++, Python, Java, and others.
Simplicity & readabilityPlain English plus a few keywords. Anyone can review it.
FlexibilityNo strict syntax, so it is easy to revise while designing.
AccessibilityClassmates, clients, and teachers can follow the logic.
One step, many languages
PseudocodeDISPLAY "Hello, BulSU!"
C++cout << "Hello, BulSU!";
Pythonprint("Hello, BulSU!")
JavaSystem.out.println("Hello, BulSU!");

Suggested time: about 4 min

Teaching tips

  • There is no single official pseudocode standard. What matters is consistency, and this class uses the keyword table on the next slide.
  • Use the "many languages" table to sell language independence. The C++ line is a preview of Lab 2.
  • Pseudocode is widely used in computer science education for algorithm design, analysis, and communication.

Common student pitfalls

  • Writing paragraphs, which is too vague.
  • Writing real C++ with semicolons and braces, which is too specific.

Ask the class

  • "Who is the audience of pseudocode?" (People: teammates, instructors, and future you. Never the compiler.)

Commonly Used Pseudocode Keywords

Input

INPUTREADENTERGET

Output

OUTPUTDISPLAYWRITE

COMPUTE area = 3.1416 * radius ^ 2

Others
IF · ELSE · ENDIFSelection: choose between two paths
WHILE · DO · ENDWHILERepeat while a condition is TRUE (tested first)
REPEAT · UNTILRepeat until a condition is TRUE (runs at least once)

The keywords at work

// This program adds numbers until 0 is entered.
START
    SET total = 0
    REPEAT
        PROMPT "Enter a number (0 to stop):"
        GET num
        ADD num TO total
    UNTIL num = 0
    DISPLAY "Total = ", total
END

Write KEYWORDS in uppercase and variable_names in lowercase so they stand apart.

Suggested time: about 5 min

Teaching tips

  • Synonyms in a column are interchangeable (INPUT, READ, ENTER, GET), but students should stay consistent within one solution. PRINT is also widely accepted as an output keyword.
  • PROMPT shows a message before input. Pair it with GET or INPUT, as in the sample.

Common student pitfalls

  • Using a variable before it has a value, e.g., ADD num TO total without SET total = 0.
  • DISPLAY "total" prints the word total. DISPLAY total prints its value.
  • Using DISPLAY where INPUT is meant.

Ask the class

  • "If the first number entered is 0, how many times does the loop body run?" (Once. REPEAT…UNTIL tests at the end.)

Lab 1 · Pseudocode

Operators & Order of Precedence

Arithmetic, highest precedence first
#OperatorMeaning
1( )Grouping: equations in parentheses first
2** or ^Exponentiation
3* / %Multiply, divide, modulus (remainder), left to right
4+ -Add, subtract, left to right

Relational (selection)

  • > greater than
  • < less than
  • >= greater than or equal to
  • <= less than or equal to
  • = equal to
  • <> not equal to

Logical

  • AND: if any condition is false, the whole expression is false
  • OR: if any condition is true, the whole expression is true
  • NOT: reverses the result (true ↔ false)

Evaluate step by step

10 + 6 / 2 * 3 - 4 % 3

  1. 6 / 2 = 3 → 10 + 3 * 3 - 4 % 3
  2. 3 * 3 = 9 → 10 + 9 - 4 % 3
  3. 4 % 3 = 1 → 10 + 9 - 1
  4. 10 + 9 = 19 → 19 - 1
  5. 19 - 1 = 18 Answer: 18

With grouping: (10 + 6) / 2 * 3 = 16 / 2 * 3 = 24.
Logical: with age = 25, age >= 18 AND age <= 60 → TRUE AND TRUE → TRUE.

Suggested time: about 8 min

Teaching tips

  • Click Show next step one step at a time and have students predict each line before you reveal it.
  • * / % share one level and are evaluated left to right, so this is not a strict "PEMDAS".
  • Modulus gives the remainder. num % 3 = 0 means "num is divisible by 3", which sets up the seatwork.
  • Inside conditions, = means comparison. Use SET for assignment to avoid confusion.
  • Where relational and logical operators sit relative to each other varies by language. Usual convention: arithmetic, then relational, then NOT, AND, OR. Lab 4 covers C++ precedence in depth.

Common student pitfalls

  • Evaluating strictly left to right (10 + 6 = 16 first).
  • Reading % as "percent".
  • Writing 18 <= age <= 60 instead of age >= 18 AND age <= 60.
  • In C++, 7 / 2 is 3 (integer division). In pseudocode, assume normal division unless told otherwise.

Ask the class

  • 7 % 3? (1) · 2 + 3 * 4? (14) · (2 + 3) * 4? (20) · NOT (5 > 3)? (FALSE)

Lab 1 · Pseudocode · ILO 3

How to Write Pseudocode

  1. Start with a statement of the main goal or aim of the pseudocode.
  2. Indent the statements inside if-else, for, and while blocks, just as in a program.
  3. Use appropriate naming conventions.
  4. Use the appropriate keywords.
  5. Elaborate everything that will happen in the actual code. Don't make it abstract.
  6. Use standard structures: if-then, for, while, cases.
  7. Check that every section is complete, finite, and clear.
  8. Don't write the pseudocode in a complete programmatic manner.

Needs work

check number
if even print even
else { cout << "odd"; }

No goal statement, vague steps, C++ syntax, and no END markers.

Follows the rules

// This program will allow the user to check
// whether a number is even or odd.
START
    PROMPT "Enter a number:"
    GET number
    IF number % 2 = 0 THEN
        DISPLAY "Even"
    ELSE
        DISPLAY "Odd"
    ENDIF
END

Suggested time: about 5 min

Teaching tips

  • The good example builds on the goal statement in the original deck: "This program will allow the user to check the number whether it's even or odd."
  • Ask students to find every problem in "Needs work" before you explain it: no goal, vague wording, C++ syntax, no ENDIF or END, no indentation.

Common student pitfalls

  • Missing ENDIF or ENDWHILE.
  • Inconsistent indentation.
  • Over-abstract steps such as "process the data".
  • Loops with no exit condition, so the pseudocode is not finite.

Ask the class

  • "Which rule does if even print even break?" (Rule 5, be elaborate, and rule 4, keywords.)

Lab 1 · Flowcharts · ILO 3

What is a Flowchart?

A type of diagram that represents an algorithm or process, showing the steps as boxes of various kinds and their order by connecting them with arrows.

A pictorial or diagrammatic representation of the flow of steps to solve a given problem.

Why engineers still use them

  • See the logic at a glance, including branches and loops.
  • Communicate a design to teammates and non-programmers.
  • Document systems and find logic errors before coding.

Origin

  1. 1921Frank Gilbreth introduces flowcharts to the American Society of Mechanical Engineers. At first they were called "Process Flow Charts".
  2. 1947Goldstine and von Neumann use "flow diagrams" to plan computer programs.
  3. 1970ANSI standardizes flowchart symbols for information processing.
  4. 1985ISO 5807 sets the international flowchart symbols still used today.

Suggested time: about 3 min

Teaching tips

  • Real-life flowcharts students already know: the university enrollment process, appliance troubleshooting guides, an ATM transaction.
  • CpE connection: they will draw close cousins of flowcharts later, such as state diagrams in digital logic design and UML activity diagrams.
  • The syllabus lists digital flowcharting tools for Lab 1. A free option is draw.io (diagrams.net), which also has an offline desktop app.

Common student pitfalls

  • Thinking flowcharts are obsolete. Industry still uses them for documentation and process design.

Ask the class

  • "Where have you followed a flowchart in real life without knowing it?"

Lab 1 · Flowcharts · ILO 3

Flowchart Symbols

Flow Line

An arrow from one symbol to another. Control passes to the symbol it points to. It can be solid or dashed.

Terminal

A rounded rectangle (stadium or oval). Marks the start or end of a process: "Start", "End".

Process

A rectangle. Shows that something is performed, e.g., "Add 1 to X" or "save changes".

Decision

A diamond. A Yes/No or True/False question with two exits, usually at the bottom and right points. Always label the exits.

Input / Output

A parallelogram. Receives data or displays results, e.g., "Get X from the user", "Display X".

Annotation

A comment or remark about the flowchart. Like code comments, it does not change the logic.

Predefined Process

A rectangle with double vertical edges. A complex step detailed in a separate flowchart, e.g., PROCESS-FILES.

Preparation

A hexagon (initialization). Prepares a value for a later step, and can stand in for a Decision in conditional loops.

On-Page Connector

A circle. Joins several flows into one exit, or links breaks and loops on the same page.

Off-Page Connector

A home-plate pentagon. Like the on-page connector, but continues the flowchart on another page.

Suggested time: about 8 min

Teaching tips

  • Almost every lab problem uses the "big five": Terminal, Input/Output, Process, Decision, and Flow Line.
  • Have students sketch each symbol on scratch paper as you name it. Then point at a random card and ask for its name and use.
  • A Decision with more than two arrows usually means it should be split into more decisions or replaced by a Predefined Process (from the original symbol table).
  • On-page connectors are also where several flows merge into one exit, such as the dot where our IF branches rejoin.

Common student pitfalls

  • Using a rectangle (Process) for input or output instead of the parallelogram.
  • Drawing Start/End as a small circle, which looks like an on-page connector. Use the stadium shape.
  • Leaving Decision exits unlabeled.
  • Writing a whole paragraph inside a symbol. Keep it to one short statement.

Lab 1 · Flowcharts · ILO 3

General Rules for Flowcharting

  1. All boxes of the flowchart are connected with arrows or flow lines.
  2. Symbols have an entry point on the top with no other entry points. The exit point is on the bottom, except for the Decision symbol.
  3. The Decision symbol has two exit points: one at the bottom and one on a side.
  4. A flowchart generally flows top to bottom. An upward flow is allowed as long as it does not exceed 3 symbols.
  5. Connectors are used to connect breaks in the flowchart.
  6. All flowcharts start and end with a Terminal symbol.

Suggested time: about 5 min

Teaching tips

  • These six rules are quoted from the Lab 1 deck. Every flowchart on this site follows them, including Decision exits at the bottom and one side.
  • Rule 4 in practice: in the seatwork loop, the return arrow goes up past exactly 3 symbols.
  • The rubric criterion Structure, Readability & Standards (×5, 25 pts) checks proper symbols and clear labels. These rules are how students earn those points.

Common student pitfalls

  • Unlabeled Decision exits.
  • Arrows missing, or pointing both ways.
  • Lines crossing everywhere. Use connectors instead.
  • Several Start terminals, or branches that never reach End.

Ask the class

  • "How many exits does a Decision have? A Process?" (Two. One.)

Lab 1 · Checkpoint

Quick Check

Think, pair, share. Open an answer only after the class has committed to one.

1Which flowchart symbol do you use for INPUT grade?

The parallelogram (Input/Output).

2How many exits does a Decision symbol have, and what must they show?

Two exits, at the bottom and one side, each labeled Yes/No or True/False.

3Evaluate 8 + 12 % 5 * 2.

12 % 5 = 2, then 2 * 2 = 4, then 8 + 4 = 12.

4"Keep asking for the password until it is correct." Which structure is this?

Loop (repetition), e.g., REPEAT … UNTIL password = correct.

5Is "an algorithm is the complete program" true or false?

False. An algorithm is the core logic of a problem, not the complete code.

6Spot the bug: SET n = 1 · WHILE n <= 5 DO · DISPLAY n · ENDWHILE

n never changes, so the loop is infinite. Add SET n = n + 1 inside the loop.

Teaching tips

  • Give each question 20–30 seconds, then cold-call one or two students before clicking it open.
  • This counts toward Participation / Recitation (10% of the term grade, per the syllabus).

Lab 1 · Guided Problem 2 · Sequence with computation

Problem 2: The Old Man's Puzzle

Cody and his friends stumbled upon an old man living alone in the woods. When Cody asked the old man his age, the old man replied with a puzzle: My age is the sum of The Programmer's and your teacher's ages subtracted by the age of your friend, Peter. Help Cody solve the puzzle and determine the age of the old man.

Task: Compute the age of the old man: (programmer_age + teacher_age) - peter_age.

  1. Start.
  2. Input The Programmer's age, the teacher's age, and Peter's age.
  3. Compute the sum of The Programmer's and the teacher's ages.
  4. Compute the old man's age = sum − Peter's age.
  5. Display the old man's age.
  6. End.
// This program computes the age of the old man.
START
    INPUT programmer_age, teacher_age, peter_age
    COMPUTE sum = programmer_age + teacher_age
    COMPUTE old_man_age = sum - peter_age
    DISPLAY old_man_age
END

Suggested time: about 7 min

Teaching tips

  • Translate the puzzle phrase by phrase. "The sum of The Programmer's and your teacher's ages" is the first COMPUTE. "Subtracted by the age of Peter" is the second.
  • Trace 30, 50, 10 → 70. Then try 10, 10, 40 → −20: a negative age shows why refinement and input validation matter.
  • Push for meaningful names (programmer_age, not a). They earn points under Structure, Readability & Standards.

Common student pitfalls

  • Computing before the inputs are read.
  • Putting the formula inside the I/O symbol instead of a Process box.
  • Writing programmer_age + (teacher_age - peter_age). It gives the same number, but it doesn't match the wording, and that habit causes real bugs later.

Ask the class

  • "Can this be done in one COMPUTE?" (Yes: old_man_age = programmer_age + teacher_age - peter_age. + and − go left to right. Two steps are just easier to read.)

Lab 1 · Guided Problem 3 · Selection

Problem 3: Adult or Minor?

Cody, our favorite robot, has a simple task: determine if The Programmer is an adult or minor. As you know, an adult is anyone aged 18 and above, and Cody needs your help to write a program that can do just that.

Task: Display "Adult" if age ≥ 18. Otherwise display "Minor".

  1. Start.
  2. Input The Programmer's age.
  3. If the age is 18 or above, display "Adult".
  4. Otherwise, display "Minor".
  5. End.
// This program determines whether The Programmer
// is an adult or a minor.
START
    INPUT programmer_age
    IF programmer_age >= 18 THEN
        DISPLAY "Adult"
    ELSE
        DISPLAY "Minor"
    ENDIF
END

Suggested time: about 7 min

Teaching tips

  • Read carefully: the problem asks about The Programmer's age, not Cody's.
  • Trace with 17, 18, and 19. Testing at the boundary (exactly 18) is what the rubric's normal, boundary, and edge test cases means.
  • Show that both branches meet at one point before a single End terminal.

Common student pitfalls

  • Using > instead of >=, so 18 prints "Minor".
  • Leaving the Yes/No exits unlabeled.
  • Writing DISPLAY inside the diamond.
  • Using two separate IFs (IF age >= 18 … IF age < 18 …). It works, but ELSE is cleaner and guarantees exactly one output.

Ask the class

  • "What should happen if the age entered is negative?" (Add validation, a good refinement.)

  4. Otherwise, if grade ≥ 80, display "B".
  5. Otherwise, if grade ≥ 70, display "C".
  6. Otherwise, if grade ≥ 60, display "D".
  7. Otherwise, display "F".
  8. End.
// This program converts a numerical grade
// into its letter grade.
START
    INPUT grade
    IF grade >= 90 THEN
        DISPLAY "A"
    ELSE IF grade >= 80 THEN
        DISPLAY "B"
    ELSE IF grade >= 70 THEN
        DISPLAY "C"
    ELSE IF grade >= 60 THEN
        DISPLAY "D"
    ELSE
        DISPLAY "F"
    ENDIF
END

Suggested time: about 10 min

Teaching tips

  • Key insight: why can the second test be just grade >= 80 and not grade >= 80 AND grade < 90? Because we only reach it when grade >= 90 was FALSE.
  • Trace 95, 85, 75, 65, 59, then the boundaries 90 and 89.
  • Selection in C++ (if, if-else, nested if, switch) is Lab 6.

Common student pitfalls

  • Separate IFs with no ELSE, so 95 prints A, B, C, and D.
  • Checking in the wrong order (grade >= 60 first), so every passing grade becomes D.
  • Forgetting the final ELSE for F.
  • Drawing a Decision with five exits. Each diamond has exactly two.

Ask the class

  • "How many decisions run for a grade of 45?" (All four.)
  • Extension: "Validate that the grade is 0–100 first, otherwise display Invalid grade."

Seatwork: Divisible by 3

I'm bored with just basic counting. How about we do some complex things this time? But I don't want to be associated with any number that's not divisible by 3. Think you can handle this?

Instruction: Print out all numbers from 1 to 100 that are divisible by 3, each on a separate line. Write the algorithm, pseudocode, and flowchart.

Need a hint?

Hint 1

Which structure lets you look at every number from 1 to 100? You need a loop with a counter.

Hint 2

How do you test "divisible by 3"? Use the modulus operator: num % 3 = 0.

Hint 3

Don't forget to update the counter inside the loop, or it will never end.

Expected output: 3, 6, 9, … 99, one per line (33 numbers).

Seatwork timer

10:00

Reveal answer & walkthrough
  1. Start.
  2. Set num to 1.
  3. While num is less than or equal to 100, repeat steps 4–5.
  4. If num ÷ 3 has a remainder of 0, display num.
  5. Increase num by 1.
  6. End.
// This program prints the numbers from 1 to 100
// that are divisible by 3, one per line.
START
    SET num = 1
    WHILE num <= 100 DO
        IF num % 3 = 0 THEN
            DISPLAY num
        ENDIF
        SET num = num + 1
    ENDWHILE
END

Optimized: count by 3s

// Same output, fewer steps.
START
    SET num = 3
    WHILE num <= 100 DO
        DISPLAY num
        SET num = num + 3
    ENDWHILE
END

34 loop tests instead of 101, and no modulus needed. This is step 8, Analyze & Optimize.

Alternative: REPEAT … UNTIL

// Same output using a post-test loop.
START
    SET num = 1
    REPEAT
        IF num % 3 = 0 THEN
            DISPLAY num
        ENDIF
        ADD 1 TO num
    UNTIL num > 100
END

Suggested time: about 15 min (10 working, 5 review)

Running the seatwork

  • Start the 10-minute timer and walk around the room. Open the hints one at a time only if many students are stuck.
  • Before revealing, show one or two student solutions (photos posted in the MS Teams class chat work well).
  • Reveal the answer, set the tracer speed to Turbo, and press Play. The output fills with 33 numbers while the loop arrow lights up again and again.
  • Show the optimized version: the same output in about a third of the work. That is the "Analyze & Optimize" step.
  • Initialization could also use the Preparation (hexagon) symbol. A rectangle is used here because students know it best.

Common student pitfalls

  • Forgetting num = num + 1, which creates an infinite loop.
  • Putting the increment inside the IF. num stays at 1 forever because 1 is not divisible by 3.
  • Writing num / 3 = 0 instead of num % 3 = 0.
  • Starting at 0, which prints 0 even though it is outside the range 1–100.
  • Drawing the loop arrow back to Start instead of the condition.

Ask the class

  • "How many numbers are printed?" (33.) "What changes to print multiples of 5 from 1 to 50?"
