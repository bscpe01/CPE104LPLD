Lab 15 · Introduction

What Is a Bug, and Why Find It Early?

Key concept

A bug is any difference between what a program should do (the specification) and what it actually does. Debugging is finding the cause and removing it.

History

In 1947, operators of the Harvard Mark II computer found a moth stuck in a relay and taped it into the logbook as the "first actual case of bug being found". Engineers already called defects "bugs"; this page made the word famous.

Recall the program development cycle from Lab 1: bugs are introduced while coding, but you pay for them when you find them.

The later you find a bug, the more it costs

Found while…How you noticeEffort to fix
Planning (Lab 1)Desk-checking the flowchart or pseudocode₱ · erase one step
CompilingThe compiler points to a line₱₱ · minutes
TestingA test case gives the wrong output₱₱₱ · trace, fix, re-test
After releaseUsers (or a device in the field) fail₱₱₱₱ · recalls, patches, lost trust

The ₱ signs are relative, not measured costs.

Today's habit

Test while you code, not after. Every small step you compile and run is a bug you catch at the cheap end of this table.

Suggested time: about 5 min

Teaching tips

  • CpE angle: a firmware bug in a device that has already shipped may need a recall or a field update. Compare that with fixing a flowchart on paper.
  • The moth logbook page (Sept. 9, 1947) is kept at the Smithsonian's National Museum of American History. It is a good story, but the word "bug" is older; Edison used it in the 1870s.
  • Connect to the rubric: "executes cleanly without logical or runtime errors and produces exact outputs across all normal, boundary, and edge test cases."

Common student pitfalls

  • Writing the whole program, then compiling it for the first time. Fifty errors at once is discouraging. Compile and run every few lines.

Ask the class

  • "What is the most annoying bug you have met so far in this course?" Write a few on the board; most will appear in today's bug gallery.

Four Kinds of Errors

Knowing which kind of error you have tells you where to look and which tool helps.

TypeWhen it shows upWho reports itWhat you seeTypical causes
Syntax / compile-timeWhile compilingThe compilerfile:line:col: error: …; no program is builtMissing ; or }, misspelled name, wrong types
LinkerAfter compiling, while linking the piecesThe linker (ld)undefined reference to …A function declared (prototype) but never defined, or defined with a different name
RuntimeWhile the program runsThe operating systemA crash, a freeze, or garbage valuesInteger division by zero, out-of-bounds array, null pointer, infinite loop
LogicWhile the program runsNobody: only your testsWrong output, no message at all= vs ==, integer division, wrong formula or condition

Easiest to fix

Syntax and linker errors: the tools tell you the file and often the line.

Harder

Runtime errors: you know that it failed, but you must find where.

Hardest

Logic errors: the program looks fine. Only a test with a known expected answer reveals them.

Suggested time: about 5 min

Teaching tips

  • The syllabus ILO names three kinds (syntax, runtime, logical). Linker errors are a fourth, practical kind students meet once they use prototypes (Lab 11).
  • Have students classify errors they have seen this semester into the four rows.
  • Out-of-bounds access is undefined behavior: it may crash, print garbage, or seem to work. It is not guaranteed to produce an error.

Common student pitfalls

  • Thinking "it compiles" means "it works". Compiling only rules out the first two rows.

Ask the class

  • "A program prints Average = 84 when the answer is 84.3333. Which row?" (Logic.)

Lab 15 · Compiler messages

One Mistake, Many Messages

One missing line can produce a screen full of errors. Read the first one, fix it, and recompile.

Read the hints

g++ often suggests the fix. From a program with a typo:

average.cpp:9:9: error: 'totl' was not declared in this scope; did you mean 'total'?

Cause

The line using namespace std; is missing. cout, cin, and endl live in the std namespace, so without it you must write std::cout. One missing line, three errors.

Strategy

  1. Read only the first error.
  2. Fix it, then recompile right away.
  3. Repeat. Many later errors vanish by themselves.

Suggested time: about 5 min

Teaching tips

  • Real g++ 13 output. The full output also has six "note: … declared here" lines pointing inside the standard library headers; students can ignore notes that point into files they did not write.
  • Good moment to mention once that std::cout is the full name, and using namespace std; is a shortcut used in this course.
  • Other one-mistake cascades: a missing " (unterminated string) or a missing ; after a class definition.

Common student pitfalls

  • Fixing every cout line one by one instead of the single missing line.
  • Panicking at 20+ errors. Usually only one or two mistakes cause them.

Ask the class

  • "g++ says 'did you mean total?'. Should you always accept the suggestion?" (Usually, but check: maybe the variable was never declared.)

Lab 15 · Debugging process · ILO 2

A Systematic Debugging Process

Don't guess and change things at random. Follow the same steps every time.

  1. Reproduce: find an input that shows the bug every time. Write it down as a test case.
  2. Locate: narrow down where: trace table, print statements, debugger, or comment out half the code.
  3. Understand: explain why the line is wrong before touching it. (Rubber duck!)
  4. Fix the cause with the smallest change. One fix at a time.
  5. Verify: rerun the failing test. Does it pass now?
  6. Re-test everything: normal, boundary, edge, invalid. A fix can break something else (a regression).

Suggested time: about 6 min

Teaching tips

  • This is the scientific method applied to code: observe, hypothesize (understand), experiment (fix), and check.
  • The loop goes back to Locate, not to Fix: if the tests still fail, your understanding of the cause was incomplete.
  • The bug log is required in Lab Exercise 15 and in the Final Project's test logs.

Common student pitfalls

  • Changing several things at once. If it then works, you don't know which change fixed it (or which one broke something else).
  • Skipping "Reproduce": "it failed once, but now it works" usually means the bug is still there (uninitialized variables behave like that).

Ask the class

  • "Why re-test the cases that already passed?" (A fix can break them: regression.)

Lab 15 · Techniques 2–5

Print Debugging, Rubber Duck, Divide & Conquer

2 · Print (cerr) debugging

Print labeled values at key points. cerr is the error stream: it is not buffered and is easy to find and delete later. Remove debug lines before submitting.

3 · Rubber duck

Explain the code, line by line, out loud, to a rubber duck (or a seatmate). Saying "and here i starts at 1…" often reveals the bug by itself.

4 · Divide and conquer

Comment out half the code (or print at the middle). Is the value already wrong there? Then the bug is in the first half. Repeat: a binary search on your code.

5 · Simplify the input

Shrink the failing input: 1 score instead of 50, small round numbers. Small inputs are easy to check by hand.

Suggested time: about 6 min

Teaching tips

  • The output is from a real run in a terminal (the [DEBUG] lines go to cerr, which appears in the same console window).
  • Print debugging works everywhere, including online compilers such as Codechum that may not have a step debugger.
  • "Rubber duck debugging" comes from The Pragmatic Programmer (Hunt & Thomas). Pair students and have them explain one function to each other.
  • Technique 1 was the trace table on the previous slides; technique 6 is the debugger on the next slide.

Common student pitfalls

  • Printing values without labels (cout << x << y → "85175"). Always label.
  • Leaving debug output in the final program, which breaks the expected output.

Ask the class

  • "Which debug line first shows something unexpected?" (The missing third [DEBUG] line: only two iterations ran.)

Lab 15 · Technique 6: the debugger · watches

Using a Debugger

A debugger pauses your real program so you can run it one line at a time and watch the variables change.

BreakpointA marked line where the program pauses.
ContinueRun until the next breakpoint (or the end).
Step overRun the current line; don't go inside functions it calls.
Step intoRun the current line, entering a function it calls.
Step outFinish the current function; pause back in its caller.
WatchA variable or expression whose value is shown at every pause.
Call stackThe chain of function calls that led to this line.

Suggested time: about 7 min

Teaching tips

  • The mockup shows the buggy average program rewritten with a function computeAverage(int n) (called from main on line 18), paused at the breakpoint the second time it is hit. The values were checked with gdb: score = 90, i = 2, sum = 85, n = 3.
  • Key insight: the highlighted line has not run yet. sum is still 85 and becomes 175 after one Step over.
  • Demo live in your IDE: set the breakpoint, run with 3 and 85 90 78, add watches for i and sum, and press Step over until the loop ends after only two rounds.
  • The syllabus ILO mentions watches explicitly; make sure every student adds at least one watch today.

Common student pitfalls

  • Pressing Step into on a cout line and landing inside the standard library. Use Step out to get back, and Step over for library calls.
  • Reading a variable before its line has run and concluding it is wrong.

Ask the class

  • "Where do you put the breakpoint to see the value of sum right after the loop?" (On the return line, line 11.)

Lab 15 · Tools

Start Debugging in Your IDE

All three IDEs below drive the same GNU debugger (gdb). The program must be built with debug information (-g).

Code::Blocks

  • Use a project (File → New → Project → Console application) with the Debug build target.
  • Breakpoint: click just right of the line number (red dot), or F5.
  • Debug → Start / Continue (F8).
  • Debug → Next line (step over), Step into, Step out.
  • Debug → Debugging windows → Watches, Call stack.

VS Code (C/C++ extension)

  • Open the .cpp file. Breakpoint: click left of the line number, or F9.
  • Run → Start Debugging (F5), or the ▷ menu → Debug C/C++ File.
  • Step over F10 · Step into F11 · Step out Shift+F11 · Continue F5.
  • Run and Debug view: Variables, Watch, Call Stack.

Dev-C++

  • Turn on debug info: Tools → Compiler Options → Settings → Linker → Generate debugging information = Yes.
  • Breakpoint: click the line number (the line turns red).
  • Execute → Debug (F5).
  • Debug panel buttons: Next line, Into function, Continue, Add watch.

Online compilers

Codechum and similar online compilers usually have no step-by-step debugger. Use trace tables and labeled cerr output there, and a desktop IDE when you need breakpoints.

Breakpoints ignored?

  • The program was built without -g (Release build): rebuild in Debug.
  • Code::Blocks: debugging a single file outside a project, or a folder path with spaces, often fails.

Suggested time: about 8 min (hands-on)

Teaching tips

  • Menu names and shortcuts are the defaults in current versions (Code::Blocks 20.03, VS Code with the Microsoft C/C++ extension, Dev-C++ 5.11 / 6.x). Check them once on the lab computers and adjust the slide if your setup differs.
  • Hands-on: every student sets a breakpoint in the buggy average program, adds watches for i and sum, and steps through the loop.
  • VS Code needs a compiler and gdb installed separately (e.g. MinGW-w64 on Windows). Its default build task for C++ already includes -g.

Common student pitfalls

  • Pressing Run instead of Debug: the program runs normally and ignores breakpoints.
  • A program waiting for cin looks "frozen" in the debugger. Type the input in the console window.

Ask the class

  • "Your breakpoint is inside a loop that runs 1000 times. How do you avoid pressing Continue 1000 times?" (Move the breakpoint after the loop, or use a conditional breakpoint if your IDE supports it.)

Lab 15 · Technique 7

assert: Check Your Assumptions

assert(condition); from <cassert> stops the program with a message if the condition is false.

  • The message names the file, line, function, and condition, so you know exactly which assumption failed.
  • Use assert for programmer mistakes ("this can never happen"). For user input, still validate with if/while and a friendly message.
  • Compiling with -DNDEBUG removes all asserts. Run 2 then prints Average = inf.

Suggested time: about 5 min

Teaching tips

  • Both runs are real (g++ 13, Linux). "Aborted" is printed by the terminal; it may also say "(core dumped)". On Windows, the message is similar and the program ends abnormally.
  • Here main forgot to validate the count, and the assert catches that mistake at the exact line. In a finished program, main should validate and re-ask.
  • Good asserts in projects: array indexes in range, pointers not null, a computed percentage between 0 and 100.

Common student pitfalls

  • Putting needed work inside an assert, like assert(cin >> x);. With NDEBUG the whole line disappears.
  • Using asserts as the only input validation.

Ask the class

  • "Write an assert for a function getScore(int scores[], int i) with 5 scores." (assert(i >= 0 && i < 5);)

Lab 15 · Testing · ILO 2

Designing Test Cases

A test case = an input + the output the specification says you should get. Decide the expected output before running.

Normal

Typical, valid inputs.
Grade: 85

Boundary

Exactly at, and just next to, a limit where behavior changes.
90 and 89.99

Edge

The extremes of the valid range: smallest, largest, empty, one item.
0 and 100

Invalid

Inputs the program must reject: out of range, wrong type.
-5, 105, abc

Rubric link

"Program Functionality, Testing & Debugging" (×8) asks for exact outputs across all normal, boundary, and edge test cases.

Test case table template
#CategoryInputExpectedActualPass / Fail
1Normal…………
2Boundary…………
3Edge…………
4Invalid…………

Rules

  • Expected output comes from the problem statement, never from running your program.
  • Test each boundary from both sides.
  • Copy the actual output exactly.
  • After every fix, rerun all tests (regression).

Suggested time: about 6 min

Teaching tips

  • Boundary vs edge: a boundary is where the behavior changes inside the range (89.99 → B, 90 → A). An edge is the end of the valid range (0, 100).
  • Most bugs in this course live at boundaries: > vs >=, loops that run one time too many or too few.
  • The Final Project rubric asks for test case logs; this table is that log.

Common student pitfalls

  • Running the program first and copying its output into "Expected". Then every test "passes", including the wrong ones.
  • Only testing the sample run from the problem statement.

Ask the class

  • "For a loop that reads n scores (1 to 10), what are the edge cases?" (n = 1, n = 10; invalid: 0 and 11.)

Lab 15 · Find the bug · 1 of 2

Bug Gallery: The Usual Suspects

Each snippet compiles (some with warnings) but does not do what its title says. Find the bug, then reveal.

1 · Print "Perfect!" only for 100

int grade = 85;
if (grade = 100) {
    cout << "Perfect!\n";
}
Reveal the bug

= assigns 100 (true), so it always prints and changes grade. Use ==. (-Wall warns: suggest parentheses around assignment.)

2 · Warn only above 40 °C

double temp = 25.0;
if (temp > 40); {
    cout << "Overheat!\n";
}
Reveal the bug

The ; after if (…) is an empty body; the block always runs and prints "Overheat!". Remove the ;. (-Wextra warns: empty body.)

3 · Average of 85, 90, 78

int sum = 85 + 90 + 78;
double average = sum / 3;
cout << average;   // 84?!
Reveal the bug

int / int is integer division: 253 / 3 = 84. Use sum / 3.0 or static_cast<double>(sum) / 3.

4 · Add 5 numbers

int total;
for (int i = 0; i < 5; i++) {
    int x;
    cin >> x;
    total += x;
}
Reveal the bug

total is never initialized, so it starts with a garbage value. Write int total = 0;.

5 · Print 1 to 10

for (int i = 1; i < 10; i++) {
    cout << i << " ";
}
Reveal the bug

Off by one: it prints 1 to 9. Use i <= 10. Test the last value, not just the first.

How to use this gallery

  • Read the title (the intent), then each line literally.
  • Predict the output before revealing.
  • Name the error type: syntax, runtime, or logic?
  • Which of these would -Wall -Wextra have warned about?

Suggested time: about 8 min

Teaching tips

  • Give 60 seconds per card in pairs, then reveal. Keep score for fun.
  • Warnings quoted on the cards were checked with g++ 13 (-Wall -Wextra). Bug 4 produced no warning at the default optimization level: warnings help, but they don't catch everything.
  • All five are logic errors at run time; none stops the compiler.

Common student pitfalls

  • Bug 3: believing that storing into a double "fixes" the division.
  • Bug 4: "it worked on my computer" (the garbage value happened to be 0).

Ask the class

  • "Which bugs would a boundary test catch?" (5: the last value; 2: a temperature of 25 should print nothing.)

Lab 15 · Find the bug · 2 of 2

Bug Gallery: Five More

6 · Choice 1 prints only "Add"

switch (choice) {
  case 1: cout << "Add\n";
  case 2: cout << "Sub\n";
  default: cout << "Bad\n";
}
Reveal the bug

No break: choice 1 falls through and prints all three lines. Add break; after each case. (-Wextra warns: this statement may fall through.)

7 · Read age, then full name

int age;
string name;
cin >> age;
getline(cin, name);
Reveal the bug

cin >> age leaves the Enter key ('\n') in the input; getline reads that empty line, so name is "". Add cin.ignore(); before getline (or use getline(cin >> ws, name)).

8 · Clear 5 scores

int scores[5];
for (int i = 0; i <= 5; i++) {
    scores[i] = 0;
}
Reveal the bug

Valid indexes are 0 to 4. scores[5] is out of bounds: undefined behavior (it may overwrite another variable, crash, or seem fine). Use i < 5.

9 · Return the bigger value

int& bigger(int a, int b) {
    int r = (a > b) ? a : b;
    return r;
}
Reveal the bug

It returns a reference to a local variable that is destroyed when the function ends. g++ warns (reference to local variable 'r' returned), and our test run crashed with a segmentation fault. Return by value: int bigger(…).

10 · Print each shape's real area

class Shape {
public:
    double area() const {
        return 0;
    }
};
// Circle redefines area()
Shape* s = &myCircle;
cout << s->area(); // 0
Reveal the bug

area() is not virtual, so the call uses the pointer's type: Shape::area(). Make it virtual (and use override in Circle). See Lab 14.

Pattern check

  • Initialize every variable.
  • Check loop bounds with the first and last values.
  • Compile with -Wall -Wextra; fix every warning.
  • Prefer override, break, and == habits.

Suggested time: about 8 min

Teaching tips

  • Bug 7 shows up in Lab 3-style programs (string & getline) and in Final Projects with menus. Show it live: the program skips the name prompt.
  • Bug 9: with g++ 13 the test program crashed (segmentation fault). Other compilers may print a plausible-looking number, which is worse because the bug stays hidden.
  • Bug 10 links back to Lab 14's static vs dynamic binding.

Common student pitfalls

  • Bug 8: "It didn't crash, so it's fine." Undefined behavior can look fine today and fail tomorrow.
  • Bug 6: forgetting that default also runs when cases fall through.

Ask the class

  • "Which of the ten bugs is a runtime error rather than a logic error?" (8 and 9 can crash; the rest give wrong output.)

Quick Check

1The compiler says undefined reference to 'computeTax(double)'. What kind of error, and what is the usual cause?

A linker error. The function was declared (prototype) but its definition is missing, misspelled, or has different parameter types.

2g++ reports 12 errors. Where do you start?

With the first error. Fix it and recompile; many later errors are side effects of the first one.

3The error is reported on line 8, but line 8 looks perfect. What do you check?

The line before it (line 7): a missing ;, ), or } is often only noticed on the next line.

4What is the difference between Step over and Step into?

Step over runs the whole current line, including any function it calls. Step into enters the called function so you can step through its lines.

5A loop must accept 1 to 50 items. Give one boundary/edge test and one invalid test.

Edge: 1 and 50 items. Invalid: 0 and 51 items (and a non-number). Test both sides of each limit.

6Why is a logic error harder to find than a syntax error?

Nothing reports it. The program runs and prints something; only a test with a known expected output shows that it is wrong.

Suggested time: about 6 min

Teaching tips

  • Use as a quick oral quiz: call on students by row, reveal after each answer.
  • Q5 connects to the Final Project, which must include test case logs.

Common student pitfalls

  • Q1: calling a linker error a "syntax error" because it appears when you press Build.

Ask the class

  • Follow-up to Q4: "When would you use Step out?" (When you stepped into a function you don't need to inspect.)

Running the seatwork

  • Students copy the buggy code, run it a few times, and use any technique: trace table, cerr lines, or the debugger with a watch on i and hotCount.
  • The two outputs on the slide are real consecutive runs of the same executable (g++ 13, Linux). Students' garbage values will differ, and some may see the "right" answer every time.
  • With optimization (-O2) g++ even warns: iteration 4 invokes undefined behavior and 'hotCount' may be used uninitialized.

Common student pitfalls

  • Fixing only the bug that changes the output on their machine.
  • Changing i <= 5 to i < 5 but leaving i = 1, which still skips readings[0] (36.2, a hot reading).

Ask the class

  • "Which test data would expose bug 3?" (A reading of exactly 35.0, which this data already has.)

Prep checklist

  1. Choose and analyze the problem: inputs, outputs, rules (Lab 1).
  2. Plan with flowcharts / pseudocode before coding.
  3. Design modules: functions (Lab 11) and classes (Labs 12–14). No global variables.
  4. Validate every input; use loops, arrays, and selection where they fit.
  5. Build in small steps; compile with -Wall -Wextra after each.
  6. Keep a test case log (normal, boundary, edge, invalid) and a bug log.
  7. Comment your code: file header, each function's purpose, tricky lines.
  8. Write the technical report and rehearse the demo: explain any line you wrote.
