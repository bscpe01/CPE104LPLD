Lab 13 · Bridge from Lab 12

Recap: The Trouble with Public Data

Lab 12's first Rectangle had public data. It works, but nothing stops nonsense values.

Lab 12 in five lines

  • A class is a blueprint; an object is an instance with its own data.
  • object.member reaches a member of one object.
  • A constructor initializes an object when it is created.
  • public members are usable anywhere; private ones only inside the class.
  • UML: + public, - private.

The problem

A rectangle can't have a side of −4, yet the class stores it and computes an area of −10. Any line of code anywhere can break the object.

Today's question

How can a class protect its own data, and how can new classes reuse an existing one?

Suggested time: about 4 min

Teaching tips

  • Ask the class to predict the output before running it. The program compiles with no warnings, and the bad value only shows up at run time.
  • Scale it up: in a banking app, a public balance means any function could set it to a million. That's the motivation for the BankAccount example.
  • Quick oral review of Lab 12 using the five bullets: call on students to give a code example for each one.

Common student pitfalls

  • "Just check for negatives in main." That works until another programmer forgets the check. Putting the check inside the class means it can't be skipped.

Ask the class

  • "Where should the rule 'length must be positive' live: in main, or in Rectangle?" (In Rectangle.)

Lab 13 · Encapsulation

Encapsulation: Private Data, Public Interface

Encapsulation bundles data with the functions that use it and hides the data, so that only those functions can read or change it.

The recipe

  1. Make data members private.
  2. Add public member functions for exactly what users need to do.
  3. Inside those functions, check every change.
Data integrityThe object can never hold an invalid value, such as a negative balance.
Validation in one placeWrite the rule once in the class, not in every main.
Hidden implementationChange how data is stored inside without breaking code that uses the class.
Easier debuggingIf the balance is wrong, only a few functions could have changed it.

Suggested time: about 6 min

Teaching tips

  • ATM analogy: you can press "Withdraw" and "Balance Inquiry", but you can't open the machine and grab the cash. The buttons are the public interface; the cash box is private.
  • Walk the diagram: every arrow from main() lands on a public function, and only those functions reach the private data. The dashed red line is what the compiler blocks.
  • Encapsulation also enables abstraction (Lab 12's pillar): users know what withdraw() does, not how.

Common student pitfalls

  • Thinking private makes data secure from hackers. It is a compile-time rule for programmers, not encryption.
  • Writing a getter and a setter for every member automatically. A setter with no checks is almost the same as public data.

Ask the class

  • "Name another real device with a public interface and hidden internals." (Vending machine, aircon remote, Meralco meter.)

Lab 13 · Encapsulation

Example: An Encapsulated BankAccount

Private data, public functions that check every change, and const getters that can only read.

Design decisions

  • balance starts at 0 and is private.
  • deposit() and withdraw() validate and return a bool: true = done, false = rejected.
  • There is no setBalance() on purpose: money moves only through valid deposits and withdrawals.
  • Getters are const: they read but never change the object.

Suggested time: about 6 min

Teaching tips

  • Map UML to code line by line: two - attributes become the private: section; five + operations become the public: section.
  • Returning bool lets the caller decide how to react (print a message, retry, log it). The class doesn't print anything itself, which keeps it reusable.
  • The UML shows const the C++ way. Strict UML marks read-only operations with {query}; either is fine for this course.

Common student pitfalls

  • Checking only amount > balance and forgetting amount <= 0. A withdrawal of −500 would then add money.
  • Printing error messages inside withdraw() and in main, so the message appears twice.

Ask the class

  • "Why is there no setBalance()?" (Anyone could set any amount and skip the rules.)

Trace: A Rejected Withdrawal

withdraw() refuses to take more than the balance, and main() finds out from the bool it returns.

Suggested time: about 8 min

Teaching tips

  • Run the tracer with 5000 / 7500 first. At line 24 the condition is true, so withdraw() returns false and the balance in the Memory panel stays 5000.00.
  • Then try −50 / 100: both calls are rejected and the balance stays 0.00. Then 5000 / 1200 for the normal case.
  • Point out that main never mentions balance. It can only ask the object to do things, and the object decides.

  • Calling withdraw() twice (once in the if, once again inside it), which withdraws twice.

Ask the class

  • "What should the bank do with a deposit of 0? What does our class do?" (Rejects it, because of amount <= 0.)

Lab 13 · Encapsulation

Getters and Setters with Validation

A getter returns a private value. A setter changes it, but only if the new value passes the class's rules.

Getter (accessor)Setter (mutator)
NamegetGrade()setGrade(g)
JobReturn a copy of the valueCheck, then change the value
Usuallyconst, no parametersReturns bool (or ignores bad input)

Note

Only add the setters users really need. Student has no setName(), so a name is fixed once the object is constructed.

Suggested time: about 6 min

Teaching tips

  • Run it live with 105, −1, 0, 100, and 92.5. The boundaries 0 and 100 are accepted because the test is g < 0 || g > 100.
  • After an invalid input the grade keeps its old value (0 from the constructor). That's the class protecting itself.
  • Textbooks call getters accessors and setters mutators (Gaddis, Malik). The get/set naming is just a convention.

Common student pitfalls

  • A setter that assigns first and checks later. Always check before changing the data.
  • Using && instead of || in the range check (g < 0 && g > 100 is never true).
  • A getter that returns nothing (void getGrade()) or that prints instead of returning.

Ask the class

  • "How would you change setGrade so an invalid grade becomes the nearest valid one instead?" (Clamp: below 0 becomes 0, above 100 becomes 100. A design choice.)

Lab 13 · Encapsulation

const Member Functions

Mark every function that only reads the object as const. The compiler then guarantees it changes nothing.

returnType name(parameters) const { … }

Rules

  • const goes after the parameter list.
  • Inside a const function, data members are read-only.
  • A const object or const& parameter can call only const functions.
  • Getters: const. Setters, deposit(), withdraw(): never.

A const function that tries to change data

double getGrade() const {
    grade = 100;          // not allowed!
    return grade;
}

error: assignment of member 'Student::grade' in read-only object

Forgetting const on a getter

Remove const from getGrade() in report.cpp and line 18 fails:

error: passing 'const Student' as 'this' argument discards qualifiers

Suggested time: about 5 min

Teaching tips

  • Connect to Lab 11: passing by const& avoids copying the object and promises not to change it. That promise only works if the functions called on it are const too.
  • Live demo: delete const from getGrade(), compile, and read the "discards qualifiers" message together. It's one of the most confusing g++ messages, so it's worth seeing once in class.
  • Rule of thumb for the lab exercise: if a function's name starts with get, is, or describes a calculation, make it const.

Common student pitfalls

  • Putting const in front (const double getGrade()). That makes the return value const, not the function.
  • Adding const to the prototype but not to the definition outside the class (or the reverse). They must match.

Ask the class

  • "Can withdraw() be const?" (No: it changes balance.)

Lab 13 · Inheritance

Inheritance: The "Is-a" Relationship

A derived class automatically gets the members of its base class and adds its own. Use it when the new class is a special kind of the existing one.

class Derived : public Base { … };

class Laptop : public Device {
    // Laptop gets brand, powerWatts,
    // turnOn(), and describe() from Device
    // and adds its own members here
};
Base classDerived class
also called parent or superclassalso called child or subclass

The is-a test

  • "A Laptop is a Device." ✓ Inherit.
  • "A Smartphone is a Device." ✓ Inherit.
  • "A Smartphone has a Battery." Not inheritance: make Battery a data member.

Suggested time: about 6 min

Teaching tips

  • Motivation: without inheritance, Laptop, Smartphone, and SmartWatch would each repeat brand, powerWatts, and turnOn(). Fix a bug in one copy and the others stay broken.
  • Read the arrow as "is a": Laptop → Device means "Laptop is a Device". The triangle always touches the base.
  • Use the is-a vs has-a test on a few pairs: Car/Vehicle (is-a), Car/Engine (has-a), Student/Person (is-a), Section/Student (has-a, an array of students).

Common student pitfalls

  • Drawing the UML arrow from base to derived. It points to the base.
  • Using inheritance just to reuse code when the is-a sentence sounds wrong ("a Battery is a Smartphone").

Ask the class

  • "Give one more class that could inherit from Device, and one attribute it would add." (SmartWatch: stepGoal; Printer: pagesPerMinute.)

Lab 13 · Inheritance

protected Members and Access Rules

Private base members are inherited but locked. protected opens them to derived classes while still hiding them from main.

Who can use a base-class member? (public inheritance)
Member is…Inside the class itselfInside a derived classOutside (main)
public +✓ yes✓ yes✓ yes
protected #✓ yes✓ yes✗ no
private -✓ yes✗ no✗ no
 
class Device {
protected:                  // # in UML
    string brand;
    int powerWatts;
    …
};
class Smartphone : public Device {
    …  cout << brand;       // OK: protected
};
// in main:  phone.brand = "X";   // error

error: 'std::string Device::brand' is protected within this context
What does a derived class inherit?
InheritedNot inherited
All data members, even private ones (they are in the object, just not accessible)Constructors: the derived class writes its own and calls the base one
All member functions (usable if public or protected)The destructor: each class has its own; C++ calls both automatically

Design tip

  • Default to private, even in a base class.
  • Use protected when derived classes genuinely need direct access.
  • Or keep it private and give the base class a protected or public getter.

Suggested time: about 6 min

Teaching tips

  • Read the table one row at a time. The only difference between protected and private is the middle column.
  • Analogy: a family recipe. Public: printed on the menu. Protected: shared with the children, not with customers. Private: only the cook knows it.
  • Many experienced programmers prefer private data plus protected getters even in base classes, because protected data can still be broken by any derived class. Both styles appear in textbooks, and the lab exercise uses protected for simplicity.

Common student pitfalls

  • Believing private members are "not inherited". They are inherited (they take up memory in the derived object), just not accessible by name.
  • Thinking protected lets main read the data. It doesn't (third column).

Ask the class

  • "Smartphone wants to print brand in its own function. Name two ways to allow it." (Make brand protected, or add a getter in Device.)

Lab 13 · Inheritance · Constructors

Calling the Base Constructor

Constructors are not inherited. A derived constructor builds its base part first by calling the base constructor in its member initializer list.

class Laptop : public Device {
private:
    int ramGB;

public:
    Laptop(string b, int w, int ram)
        : Device(b, w),   // 1. base part
          ramGB(ram)      // 2. own members
    {
        // 3. then the body runs
    }
};
  1. Laptop lap("Lenovo", 65, 16);
  2. Device("Lenovo", 65) sets brand and powerWatts.
  3. ramGB becomes 16.
  4. The Laptop constructor body runs.

Rules

  • Write the base class name with its arguments first in the initializer list.
  • Pass the base's values through the derived constructor's parameters.
  • The derived class can't assign the base's private members itself.

What if you leave it out?

Laptop(string b, int w, int ram) : ramGB(ram) {
    brand = b;    // error if private
}

C++ then calls Device() with no arguments, which doesn't exist:

error: no matching function for call to 'Device::Device()'

Suggested time: about 5 min

Teaching tips

  • This is why Lab 12 introduced the member initializer list: a base-class part can only be built there.
  • If Device had a default constructor, leaving out Device(b, w) would compile but give a Laptop with the default brand. That's a silent logic bug, so always call the right base constructor explicitly.
  • The comments in the code show the order; the next slide proves it with output.

Common student pitfalls

  • Calling the base constructor inside the body: { Device(b, w); }. That creates a temporary, unnamed Device that is destroyed right away; the Laptop's own Device part is unchanged.
  • Passing the arguments in the wrong order (Device(w, b)), which gives a compile error about types.

Ask the class

  • "Write the Smartphone constructor that takes brand, watts, and battery mAh." (Smartphone(string b, int w, int mah) : Device(b, w), batteryMah(mah) {})

Lab 13 · Inheritance · Trace

Constructor and Destructor Order

Base first on the way in, derived first on the way out, like putting on a shirt and then a jacket, and taking them off in reverse.

Order rule

  • Construction: base → derived (Device, then Laptop).
  • Destruction: derived → base (Laptop, then Device).

Suggested time: about 6 min

Teaching tips

  • Ask for predictions before stepping. Many students expect "Laptop constructor" first because Laptop lap; names Laptop.
  • Why base first? Laptop's constructor might use inherited members, so they must already exist. Why derived first when destroying? Laptop's destructor might still use the Device part.
  • Multilevel preview: with GamingLaptop : public Laptop, construction is Device → Laptop → GamingLaptop and destruction is the exact reverse.

Common student pitfalls

  • Thinking only the derived destructor runs. Both run automatically, and you never call either yourself.
  • Confusing this with Lab 12's rule for several objects (destroyed in reverse order of creation). That rule still holds; this one is about the parts of one object.

Ask the class

  • "Add Laptop lap2; after lap. How many lines does the program print now, and in what order?" (10 lines: lap's two constructors, lap2's two, the "Using" line, then lap2's destructors before lap's.)

Lab 13 · Inheritance · Trace

Redefining a Base-Class Function

A derived class can write its own version of a base function with the same name. To reuse the base version, call it with Device::describe().

Not virtual (yet)

Here the compiler picks the version from the object's declared type (Laptop lap → Laptop::describe()). Lab 14 adds virtual so that a Device* pointing to a Laptop can still find Laptop::describe().

Suggested time: about 7 min

Teaching tips

  • Terminology: Gaddis calls this redefining a base-class function. "Overriding" is the name used once the base function is virtual (Lab 14). Many people use "override" loosely for both.
  • Trace lap.describe(): Laptop's version prints "Laptop: ", calls Device::describe() for the shared part, then adds the RAM line. Reuse instead of copy-paste.
  • Smartphone's version prints brand directly, which works only because brand is protected in this Device.
  • Expected output: Generic, 10 W / Laptop: Lenovo, 65 W / RAM: 16 GB / Phone: Samsung, 5000 mAh.

Common student pitfalls

  • Writing describe(); instead of Device::describe(); inside Laptop's version. That calls Laptop's own function again, forever (infinite recursion, then a crash).
  • Changing the signature (e.g. describe(int), or dropping const) and expecting a redefinition. A different signature hides the base version instead. Lab 14's override keyword catches this.

Ask the class

  • "What would lap.Device::describe(); print in main?" (Lenovo, 65 W: the base version, called explicitly.)

Lab 13 · Inheritance

Types of Inheritance

Classes can be arranged in a single line, a chain, or a tree. Every arrow still means "is a".

TypeMeaningC++
SingleOne base, one derived classclass Laptop : public Device
MultilevelA derived class becomes the base of another; GamingLaptop gets Device's and Laptop's membersclass GamingLaptop : public Laptop
HierarchicalSeveral classes share one baseclass Smartphone : public Device, class SmartWatch : public Device
MultipleOne class with two or more bases (allowed in C++, but can cause name conflicts; not required in this course)class CameraPhone : public Phone, public Camera

Suggested time: about 4 min

Teaching tips

  • Today's Device/Laptop/Smartphone example is hierarchical; the lab exercise's Person/Student/Instructor is hierarchical too.
  • Multilevel shows why constructor order matters: GamingLaptop builds Device, then Laptop, then itself.
  • Multiple inheritance: mention only. If both bases have a function with the same name, calls become ambiguous. Java and C# don't allow it for classes at all.

Common student pitfalls

  • Calling a tree with three children "multiple inheritance". Multiple means one class with several parents, not one parent with several children.
  • Very deep chains (5+ levels) for small programs. Keep hierarchies shallow and use the is-a test at every level.

Ask the class

  • "Person → Student → ScholarStudent: which type is that?" (Multilevel.)

Lab 13 · Debugging

Common Pitfalls: Encapsulation and Inheritance

1 · Making data public "to make it work"

public: double balance; then acct.balance = -1000000;

Compiles fine, and every check in withdraw() is bypassed. Fix: keep it private and add the member function you actually need.

2 · Forgetting public in the base list

class Laptop : Device { … }; then lap.turnOn();

For a class, inheritance is private by default, so Device's public members become private in Laptop: 'void Device::turnOn()' is inaccessible within this context. Fix: : public Device

3 · Using a base's private member in the derived class

void show() { cout << brand; } inside Laptop

g++: 'std::string Device::brand' is private within this context. Fix: make it protected, or call a Device getter.

4 · Object slicing (a teaser for Lab 14)

Laptop lap("Lenovo", 16);
Device copy = lap;   // copies the Device part only
Device* ptr = &lap;
lap.describe();
copy.describe();
ptr->describe();

Laptop: Lenovo, 16 GB
Device: Lenovo
Device: Lenovo

copy lost ramGB (it was "sliced off"). Even the pointer runs Device's version. Lab 14's virtual fixes the pointer case.

Suggested time: about 6 min

Teaching tips

  • Messages are from g++ 13 (-Wall -Wextra). Pitfall 2 also prints 'Device' is not an accessible base of 'Laptop'.
  • Pitfall 4 uses the classes from devices.cpp, simplified: Device has brand, Laptop adds ramGB, and each has its own describe(). The output shown is real.
  • Don't solve slicing today. Leave students with the question: "ptr points to a Laptop. Why does it run Device's function?" Lab 14 answers it.
  • For struct, inheritance is public by default, which is another reason pitfall 2 surprises people who switch between the two.

Common student pitfalls

  • "Fixing" pitfall 3 by making everything public. That trades a compile error for pitfall 1.

Ask the class

  • "Which of these four does the compiler catch, and which compile silently?" (2 and 3 are errors; 1 and 4 compile.)

Lab 13 · Check your understanding

Quick Check

Answer on your own first, then click to reveal.

1Why make balance private instead of public?

So every change must go through deposit() or withdraw(), which validate the amount. The object can never hold an invalid balance.

2Balance is 5000. What does acct.withdraw(7500) return, and what is the balance afterward?

It returns false, and the balance stays 5000 because the function returns before balance -= amount.

3What does const promise in double getBalance() const?

That the function won't change any data member. The compiler enforces it, and it lets the function be called on const objects and const& parameters.

4Can a Laptop member function use Device's brand directly if it is private? If it is protected?

Private: no (compile error). Protected: yes. In both cases main still can't use it.

5GamingLaptop : public Laptop and Laptop : public Device. In what order do the constructors and destructors run for GamingLaptop g;?

Constructors: Device, Laptop, GamingLaptop. Destructors: GamingLaptop, Laptop, Device.

6"A Smartphone has a Battery." Should Smartphone inherit from Battery?

No. That's a has-a relationship, so Battery should be a data member of Smartphone. Inheritance is for is-a.

Suggested time: about 6 min

Teaching tips

  • Think-pair-share as in Lab 12. Q2 and Q5 can be verified with the tracers on earlier slides.
  • Q6 is a design question with no code. Ask for two more has-a examples from the lab room.

Common student pitfalls

  • Q2: saying the balance becomes −2500. Remind them the check happens before the change.
  • Q5: reversing the destructor order.
