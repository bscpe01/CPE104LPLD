Lab 14 · Concept

What Is Polymorphism?

Key concept

Polymorphism (Greek poly = many, morph = form) means one interface, many implementations: the same call does the right thing for each type of object.

Everyday analogy

Press the power button on a laptop, a phone, or an electric fan. Same action, but each device responds in its own way. You don't need to know which device it is to press it.

Compile-time

Function and operator overloading. The compiler picks the version from the argument types.

Run-time

virtual functions called through a base-class pointer or reference. The program picks the version while running.

Suggested time: about 5 min

Teaching tips

  • Write "one interface, many implementations" on the board and keep it there all session.
  • The diagram is the goal of today's lab. By the Shape* array slide, students will run exactly this loop.
  • Compile-time polymorphism is a short recap (Lab 11 overloading). Most of the lab is about run-time polymorphism.

Common student pitfalls

  • Confusing overloading (same name, different parameters, same scope) with overriding (same signature, redefined in a derived class through virtual).

Ask the class

  • "Name another 'same action, different behavior' example." (A remote's Play button for TV vs. speaker; a 'charge' command for a phone vs. a power bank.)

Lab 14 · Compile-time polymorphism

Compile-Time Polymorphism: Overloading

The compiler chooses which function to call by looking at the argument types, before the program runs.

  • Same name area, different parameter lists.
  • area(2.0) → 1 argument → the circle version.
  • Decided at compile time: no objects or pointers needed.
  • + now works on Vector2D (adding two forces).
  • operator<< is a friend, not a member, because the left operand is cout.
  • It returns out so you can chain <<.

Preview only: operator overloading is not required in Lab Exercise 14.

Suggested time: about 7 min

Teaching tips

  • Function overloading is a 1-minute recap from Lab 11. Ask a student to predict which area each call uses.
  • Operator overloading: show that force1 + force2 is really a call to force1.operator+(force2). Keep it brief; it is enrichment.
  • Engineering link: adding force or velocity vectors component by component, as in physics.

Common student pitfalls

  • Trying to overload by return type only (int f() vs double f()). Not allowed: the parameter lists must differ.
  • Writing operator<< as a member function. Then cout would have to be on the right side.

Ask the class

  • "What would area(3) call?" (The one-parameter version; the int 3 converts to double.)

Lab 14 · Virtual functions

The Problem: Static Binding

Continue Lab 13's example: point a Device* at a Laptop and call describe().

lap"Lenovo" | 65 | 16a Laptop object
ptr&lapdeclared as Device*

Why line 35 skips the Laptop part

  • The object is a Laptop, but ptr is declared as Device*.
  • Without virtual, the compiler binds the call using the pointer's type, at compile time.
  • This is static (early) binding.

Suggested time: about 6 min

Teaching tips

  • Run it live. Before pressing Run, ask for predictions of line 35. Many students expect the "Laptop: … RAM" text, as in Lab 13's lap.describe().
  • Explain why we want base pointers at all: a single array or function that handles every device (laptops, phones, routers) without knowing their exact types.
  • Lab 10 link: ptr->describe() is the same as (*ptr).describe().

Common student pitfalls

  • Thinking the compiler "looks inside" the pointer. It only knows the declared type unless the function is virtual.
  • Trying Laptop* lp = &someDevice; (base to derived). That direction does not compile without a cast.

Ask the class

  • "Which is legal: Device* p = &lap; or Laptop* p = &d; (where d is a Device)?" (Only the first. A Laptop is a Device.)

Suggested time: about 7 min

Teaching tips

  • Live-code it: add the single word virtual to the Device::describe() line of the previous program and rerun. Then add Smartphone and the array.
  • Point out that the for loop never mentions Laptop or Smartphone. Adding a Router class later needs no change to the loop. That is the payoff.
  • "Overriding" = a derived class supplies its own version of a virtual function with the same signature.
  • Optional depth: the compiler keeps a hidden table of function addresses (a "vtable") for classes with virtual functions. Not needed for the exercise.

Common student pitfalls

  • Putting virtual only in the derived class. It must be in the base class (once virtual, always virtual in derived classes).
  • Calling through an object (lap.describe()) and expecting to "see" polymorphism. You need a base pointer or reference.

Ask the class

  • "What do we change in main to add a SmartWatch?" (Create it and put its address in the array. The loop stays the same.)

Lab 14 · Virtual functions

override: Let the Compiler Check You

A function overrides only if its name, parameters, const, and return type all match the base version.

Add override on line 23:

void describe() override {     // forgot const

Habit

Write override on every overriding function. A typo becomes a compile error instead of a hidden logic bug. Fix here: void describe() const override.

Suggested time: about 5 min

Teaching tips

  • The two outputs are real g++ 13 messages (trimmed). The -Woverloaded-virtual warning is part of -Wall in g++ 13; older compilers (such as the one bundled with many Dev-C++ installs) may compile this with no warning at all.
  • Make the point: a warning can be ignored, an error cannot. override turns a silent logic bug into an error at a specific line.
  • override is C++11 and later. Codechum and modern IDEs support it.

Common student pitfalls

  • Missing const, a different parameter type (int vs double), or a misspelled name (Describe).
  • Writing override in the base class. It belongs in the derived class only.

Ask the class

  • "Would void describe(int level) const override compile?" (No. The parameter list differs, so it does not override anything.)

Lab 14 · Abstract classes

Pure Virtual Functions & Abstract Classes

A plain "Shape" has no real area. Say so with = 0, and C++ stops anyone from creating one.

Key concept

  • A pure virtual function (= 0) has no body in the base class: "every shape must have an area, but I can't compute it here."
  • A class with at least one pure virtual function is an abstract class. It exists only to be inherited.
  • A derived class must override every pure virtual function, or it is abstract too.

Shape s; ✗ error · Shape* p = &c; ✓ · const Shape& s ✓

Suggested time: about 7 min

Teaching tips

  • Live: change Shape in shapes.cpp, rerun (same output), then add Shape s; in main and read the error together.
  • Read the "note" lines: g++ even lists which functions are still pure. If a derived class forgets one override, the same note tells you which one.
  • Design view: an abstract class is a contract. "Anything that claims to be a Shape must provide area() and name()."

Common student pitfalls

  • Writing virtual double area() const = 0 { } or forgetting the = 0.
  • Forgetting to override one pure function in a derived class, then getting "cannot declare variable 'c' to be of abstract type 'Circle'".

Ask the class

  • "Can an abstract class have normal (non-virtual) functions and data members?" (Yes. Sensor on a later slide has both.)

Lab 14 · Dynamic objects

Virtual Destructors

With new, you often hold a derived object in a base pointer. delete must run the derived destructor too.

Without virtual, g++ -Wall also warns: deleting object of polymorphic class type 'Device' which has non-virtual destructor might cause undefined behavior.

What went wrong

~Laptop() never ran, so the log was never freed: a memory leak. Officially this is undefined behavior; the output is what g++ did.

Rule

If a class has any virtual function, give it a virtual destructor.

Suggested time: about 6 min

Teaching tips

  • Order of destruction is the reverse of construction: derived first, then base. Students saw constructor chaining in Lab 13; this is the mirror image.
  • Both outputs are real runs with g++ 13. A memory checker (Valgrind) reported "96 bytes definitely lost" for the non-virtual version (24 ints × 4 bytes).
  • Lab 10 link: every new needs exactly one delete; new[] pairs with delete[].

Common student pitfalls

  • Making only the derived destructor virtual. It is the base destructor that must be virtual.
  • Ignoring the -Wdelete-non-virtual-dtor warning because "it still runs".
  • Using delete instead of delete[] for an array made with new[].

Ask the class

  • "Why didn't the program crash if memory leaked?" (A leak doesn't stop a short program. It hurts long-running programs, such as firmware that runs for months.)

Lab 14 · Pitfall

Pitfall: Object Slicing

Pass a derived object by value as a base object, and only the base part is copied. The rest is "sliced off".

lap"Lenovo" | 65 | 16Laptop
d (copy)"Lenovo" | 65only a Device

Fix

Pass by reference (const Device&) or by pointer (Device*), as in Lab 11. Never store derived objects in an array of base objects.

Good to know: dynamic_cast

Laptop* lp = dynamic_cast<Laptop*>(ptr); gives nullptr if ptr does not point to a Laptop (needs a class with a virtual function). Use it rarely; prefer a virtual function.

Suggested time: about 5 min

Teaching tips

  • Same object, same virtual function, two different results. The only difference is Device d vs const Device& d in the parameter list.
  • Lab 11 link: pass-by-value makes a copy; pass-by-reference uses the caller's variable. With classes, the copy is made as the parameter's type (Device), so it truly is a Device.
  • dynamic_cast is optional enrichment. If a design needs many dynamic_casts, a virtual function is usually missing.

Common student pitfalls

  • Shape shapes[3] = {c, r, t}; compiles (when Shape is not abstract) but slices every element.
  • With an abstract base, void f(Shape s) does not even compile, which is one more benefit of abstract classes.

Ask the class

  • "Why does const appear in const Device&?" (The function only reads the object; const prevents accidental changes and allows passing temporaries.)

Lab 14 · Avoid these

Common Polymorphism Pitfalls

1 · No virtual in the base

Base pointers call the base version (static binding).

Fix: virtual on the base function.

2 · Signature mismatch

Missing const or a different parameter type creates a new function instead of overriding.

Fix: always write override.

3 · Slicing

Passing or storing a derived object by value as a base object.

Fix: use const Base& or Base*.

4 · Missing virtual destructor

delete basePtr; skips the derived destructor (undefined behavior, leaks).

Fix: virtual ~Base() {}

5 · Creating an abstract object

Shape s; or new Shape() will not compile.

Fix: create a concrete derived class (Circle).

6 · new without delete

Every object made with new leaks if you never delete it.

Fix: one delete per new, in a loop for arrays of pointers.

Suggested time: about 4 min

Teaching tips

  • Use this as a checklist for Lab Exercise 14. Students can check their own code against all six before submitting.
  • Pitfalls 1, 2, and 4 compile (sometimes with warnings) and give wrong behavior. Pitfall 5 is a compile error. Point out that errors are friendlier than silent bugs.
  • Lab 15 (Debugging) has a "bug gallery" that includes the missing-virtual bug.

Common student pitfalls

  • Fixing the symptom (casting pointers around) instead of the cause (a missing virtual).

Ask the class

  • "Which of these six can the compiler catch for you?" (5 always; 2 with override; 4 often as a warning with -Wall.)

Lab 14 · Check your understanding

Quick Check

1In your own words, what is polymorphism?

One interface, many implementations: the same call (like s->area()) runs different code depending on the actual type of the object.

2describe() is NOT virtual. Device* p = &lap; p->describe(); runs which version?

Device::describe(). Without virtual, the call is bound at compile time using the pointer's type (static binding).

3Overloading or overriding: area(double r) and area(double w, double h) in the same file?

Overloading (compile-time polymorphism): same name, different parameter lists. Overriding is a derived class redefining a virtual function with the same signature.

4Why does Shape s; fail when Shape has virtual double area() const = 0;?

Shape is an abstract class: it has a pure virtual function with no body, so C++ will not create objects of it. Pointers and references to Shape are still fine.

5What does override add if the code already works without it?

A compile-time check. If the function does not really override a base virtual function (wrong const, parameters, or name), the compiler reports an error instead of silently creating a new function.

6When does a base class need a virtual destructor?

Whenever derived objects may be deleted through a base pointer, which in practice means any class with virtual functions. Otherwise only the base destructor may run (undefined behavior, leaks).
